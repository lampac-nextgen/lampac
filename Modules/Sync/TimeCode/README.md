# TimeCode

Учёт и синхронизация **таймкодов**: данные в **SQLite** через **`SqlContext`**, API под **`/timecode/`**, JS-плагин **`timecode.js`** (на диске шаблон **`plugin.js`**).

Пространство имён: **`TimeCode`**.

## Ключи

Запись адресуется двумя способами, и оба — первого класса.

| Колонка | Кто пишет | Значение |
|---------|-----------|----------|
| **`identity`** | нативные клиенты | `movie-674`, `tv-1851-s1e2`, `tv-1851` |
| **`item`** | веб-Lampa | хеш `Utils.hash(original_title)` / хеш эпизода |
| **`card`** | оба | `1851_tv` — группировка по карточке |

Веб-Lampa знает про запись только хеш (`Lampa.Timeline` дергается по нему), поэтому отдать ей другой ключ нельзя, не переписав фронтенд. Нативный клиент, наоборот, знает TMDB-идентичность и не должен страдать от коллизий хеша: один хеш достаётся двум одноимённым тайтлам («The Running Man» 1987/2025) и фильму с сериалом одновременно.

Отсюда одна строка с двумя индексами:

- `UNIQUE (user, card, item)` — путь веба;
- `UNIQUE (user, identity) WHERE identity IS NOT NULL` — путь нативных клиентов.

`card` выводится из `identity`, когда клиент её не прислал: `movie-674` → `674_movie`, `tv-1851-s1e2` → `1851_tv`. Правило живёт в одном месте (`CardOf`), поэтому на проводе достаточно одного `id` — разобранные `type`/`tmdb_id`/`season`/`episode` не передаются, чтобы не иметь двух представлений одного факта.

`identity` у строки из веба берётся **из самой записи**, если веб её донёс: road — блоб, который куб хранит дословно и возвращает как есть (так в него попал и `updated`, которого у куба изначально не было). Поэтому `id` внутри road доезжает через куб до плагина, а плагин — до нас, и хеш остаётся только адресом.

Если `id` в road нет, у **фильма** идентичность всё равно выводится: `card_id` — это `{tmdb}_movie`, то есть `674_movie` и есть `movie-674`. Так что фильмам патч клиента не нужен вообще — ни новым записям, ни уже накопленным (миграция вписывает им identity задним числом).

**Сериалам нужен**: `1851_tv` называет шоу, а какая это серия — знает только хеш, и он необратим. `tv-1851` серии присвоить нельзя, это идентичность шоу целиком. Пока `id` в road не появился, такая строка живёт по хешу и получит identity при первой записи, которая её донесёт.

Обратно тоже: `/timecode/all` кладёт `id` в road, так что веб, прочитав запись, знает её идентичность. Нативному клиенту стоит присылать `hash` — иначе его запись не попадёт в легаси-выдачу, которая ключуется хешем.

## Два штампа

| Поле | Кто ставит | Зачем |
|------|------------|-------|
| **`watched_at`** | клиент, мс | **Когда смотрели.** Этим арбитрируются конфликты между устройствами |
| **`updated_at`** | сервер, мс | **Когда приняли строку.** Курсор дельт: `?since=` селектит `updated_at > since` |

Одно другим не заменяется. Отложенная отправка (офлайн, убитое приложение, лежащий роутер) разносит их на часы: досмотрел в 23:40, строка уехала в 09:15.

- Только по `updated_at`: вчерашняя строка, доехавшая утром, победит честную утреннюю запись с другого устройства. Мердж инвертирован.
- Только по `watched_at`: строка со старым штампом окажется позади курсора, который другие устройства уже подняли, и не доедет до них никогда.

`updated_at` монотонен внутри пользователя: штамп берётся как `max(сейчас, последний + 1)`. Без этого две строки, принятые в одну миллисекунду, получили бы одинаковый курсор, и `> since` потерял бы вторую — при массовой записи это гарантированная потеря. Цена: пачка занимает по миллисекунде на строку и курсор может уйти вперёд реального времени на длину пачки.

Клиентский штамп не проверяется на вменяемость **здесь** — устройство со сломанными часами выиграет любое сравнение. Это осознанно оставлено клиенту: у него есть контекст (сравнить с локальным временем просмотра), у сервера — нет.

## Удаление

Снятая отметка — строка с **`deleted = 1`**, а не `percent = 0`. Строка остаётся в базе: без неё следующий `dump` вернёт запись обратно с другого устройства.

`duration` у надгробия **сохраняется** — из неё Lampa считает позицию при повторной отметке (`episode/module/mark.js`), обнулять её значит сломать следующий toggle на всех клиентах. `position` и `percent` обнуляются.

Легаси-выдача `/timecode/all` надгробия не отдаёт, так что веб видит запись исчезнувшей. Убрать её из уже закешированного `file_view` веб-Lampa не умеет (плагин только доливает ключи, удалять их ему нечем) — это ограничение фронтенда, не сервера.

## HTTP (`TimeCodeController`)

### Легаси — веб-Lampa, контракт неизменен

| Маршрут | Метод | Назначение |
|---------|-------|------------|
| **`timecode.js`**, **`timecode/js/{token}`** | **GET** | Читает **`{modpath}/plugin.js`**, подставляет **`{localhost}`**, **`{token}`** |
| **`/timecode/all`** | **GET** | Query **`card_id`** → `{ хеш: "json-строка road" }` по одной карточке |
| **`/timecode/add`** | **POST** | Query **`card_id`**, form **`id`** (хеш), **`data`** (road) |

road-объект (`duration`, `time`, `percent`, `profile`, `updated`) собирается из колонок на чтении и раскладывается по ним на записи. Ключи road, которым нет колонки, уезжают в **`extra`** и возвращаются на месте — обновление Lampa не потеряет новое поле.

### Нативные клиенты

| Маршрут | Метод | Назначение |
|---------|-------|------------|
| **`/timecode/dump`** | **GET** | Всё, что есть у пользователя, включая надгробия |
| **`/timecode/changelog`** | **GET** | Query **`since`**, **`limit`** (≤20000) — дельты по `updated_at > since` |
| **`/timecode/set`** | **POST** | Тело: одна строка, массив или `{ "rows": [...] }`. Удаление — та же строка с `"deleted": true` |

Строка на проводе:

```json
{
  "id": "tv-1851-s1e2",
  "hash": "a3f1c2…",
  "card": "1851_tv",
  "position": 2580.0,
  "duration": 2580.0,
  "percent": 100.0,
  "watched_at": 1755698000000,
  "updated_at": 1755698001204
}
```

Ответ `dump` / `changelog`: `{ version, rows: [...] }`, у `changelog` ещё `truncated`. `version` — курсор для следующего `?since=`, и двигается он только по фактически отданному, иначе усечённый по `limit` хвост потеряется.

Ответ `set`: `{ success, version, accepted, skipped }`. **`skipped` — не ошибка:** строка с `watched_at` старше уже лежащей не пишется. Так очередь офлайн-устройства, доехавшая через десять часов, не затирает свежую запись с другого устройства.

Отдельного флага «просмотрено» нет: это `percent`. road Lampa его не несёт и не несла никогда, порог завершённости — политика клиента, а не свойство записи. Понадобится «видел, но место не трогай» — тогда флаг и появится, вместе с клиентом, который умеет так отмечать.

`/timecode/set` идемпотентен по `id`: повтор той же строки только сдвинет `updated_at`.

## Шина

Запись рассылается через **`NwsEvents`** событием **`timecode`** с payload `{ version, ids }` — клиенту достаточно узнать, что пора спросить `changelog`.

Отправителя шина исключает сама (`NwsEvents.SendAsync` сравнивает `connectionId`), поэтому своё же эхо до автора записи не доходит. Это принципиально: клиент, который применяет собственный апдейт как чужой, дёргает локальный стор, тот триггерит синхронизацию, шина возвращает событие снова — и два устройства гоняют прогресс по кругу вечно. Оба пишущих маршрута принимают **`connectionId`** в query; `plugin.js` подставляет `window.lwsEvent.connectionId`.

## Схема и миграция

Таблица **`timecodes`**, модель **`SqlModel`** — в **`SqlContext.cs`**. БД SQLite **`database/TimeCode.sql`** (отдельно от **`database/Sync.sql`** модуля **Sync**).

Старая схема хранила весь road строкой в колонке **`data`**, а колонку **`updated`** писала и **никогда не читала** — ни выдача, ни фильтрация её не касались. `MigrateLegacyBlob` разбирает блоб в типизированные колонки один раз, на старте: таблица пересоздаётся (меняется форма уникальных индексов, и EF не сможет вставлять строки в таблицу, где остался `updated NOT NULL` без значения по умолчанию), данные переливаются через `json_extract`. Строки с невалидным JSON в `data` отбрасываются — восстанавливать из них нечего.

Записи, у которых `data` был валиден, получают `watched_at` из `road.updated` и `updated_at` из старого серверного `updated`. Фильмам сразу вписывается `identity` из `card` — её получает свежайшая строка карточки, потому что один фильм мог накопить два хеша при смене `original_title`, а идентичность у них одна. Дубли курсора в исторических данных возможны и безвредны: первый заход клиента — это всегда `dump`, а не `changelog`.

Пишущие запросы сериализуются семафором **на пользователя** (`SqlContext.SemaphoreKeyFor`), а не на всю базу: раньше любая запись любого аккаунта ждала любую другую.

## Связь с Sync / Storage / DatabaseEditor

**Sync** создаёт каталоги **`database/storage`** и хранит закладки в **`database/Sync.sql`**. **DatabaseEditor** правит таблицу `timecodes` напрямую: он по-прежнему показывает road-объект, но собирает его из колонок и раскладывает обратно (`TimeCodeRoad` / `TimeCodeAssignments` в `DatabaseStore.cs`), а правка поднимает `updated_at` выше всех строк пользователя, иначе клиенты её не увидят.
